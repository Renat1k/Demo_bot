# Перукарня «Найкраща» — Telegram-бот

Telegram-бот для перукарні в Києві. Інтерфейс — українською.
Реалізовано онлайн-запис із перевіркою тривалості послуг, 5-хвилинним
утриманням слота, SQLite-заявками, сповіщеннями майстру/клієнту та
адмін-панель. Оплати й реального графіка майстра ще немає.

## Архітектура

```text
bot-2/
├── bot.py              # Application, polling, health-сервер, cleanup-потік
├── config.py           # env, послуги, графік, пороги, контакти
├── database.py         # SQLite: утримання, заявки, перевірка перетинів
├── schedule.py         # дати, слоти, перерви, тривалість, правила скасування
├── notifications.py    # безпечна доставка сповіщень майстру/клієнту
├── texts.py            # українські тексти та підписи
├── keyboards.py        # inline-клавіатури та callback-константи
├── web.py              # Flask health-сервер для Render
├── handlers/
│   ├── __init__.py     # реєстрація; catch-all callback останній
│   ├── common.py       # /start, /menu, /help, головне меню, error handler
│   ├── user.py         # запис, послуги, мої записи, скасування
│   └── admin.py        # адмін-панель, фільтри, пагінація, дії майстра
├── tests/
│   ├── __init__.py
│   ├── test_booking.py # SQLite: гонки, перетини, істечення, міграції
│   ├── test_handlers.py # сценарії, доступи, сповіщення, реєстрація
│   └── test_schedule.py # графік, перерви, тривалість, вікно запису
├── requirements.txt
├── runtime.txt
├── render.yaml
├── .env.example
├── .gitignore
└── README.md
```

Потік клієнта: меню → послуга → дата → час → утримання → підтвердження →
заявка `pending` → рішення майстра. Заявка зберігається в SQLite, а не лише
в `context.user_data`.

## Локальний запуск

Потрібен Python 3.11+.

```bash
python -m venv .venv
```

Windows:

```powershell
.venv\Scripts\Activate.ps1
```

Linux/macOS:

```bash
source .venv/bin/activate
```

Встановлення залежностей:

```bash
pip install -r requirements.txt
```

`tzdata` у requirements потрібен для коректної роботи `zoneinfo` на Windows
та в мінімальних контейнерах. Без нього код має UTC-fallback, але локальний
час салону може відрізнятися.

Змінні середовища:

```powershell
$env:BOT_TOKEN = "токен_від_BotFather"
$env:ADMIN_CHAT_ID = "ваш_telegram_id"
$env:DB_PATH = "bot.db"   # необов'язково
python bot.py
```

`ADMIN_CHAT_ID` необов'язковий: без нього бот працює, але адмін-панель і
сповіщення майстру недоступні. `PORT` необов'язковий; локально health-сервер
використовує 10000. Файл `.env.example` — лише шаблон; бот не завантажує
`.env` автоматично, тому змінні треба задати в терміналі або на хостингу.

Щоб дізнатися свій `ADMIN_CHAT_ID`, напишіть боту будь-яке повідомлення та
відкрийте `https://api.telegram.org/bot<ТОКЕН>/getUpdates`. Значення
`message.from.id` — це ваш ID.

## Тести

Тести не потребують Telegram-токена або реального PTB: для SQLite
використовується тимчасова база, для обробників — локальні заглушки
Telegram-об'єктів. Окремо перевіряються графік і реєстрація callback-ів.

```bash
python -m unittest discover -s tests -v
```

## Render

У репозиторії є `render.yaml`. Створіть Blueprint або Web Service вручну.
Якщо в репозиторії є інші проєкти, вкажіть **Root Directory: `bot-2`**.

- Build Command: `pip install -r requirements.txt`
- Start Command: `python bot.py`
- Health Check Path: `/health`
- Environment:
  - `BOT_TOKEN` — токен від BotFather;
  - `ADMIN_CHAT_ID` — ваш Telegram ID;
  - `DB_PATH` — необов'язково, шлях до SQLite-файлу;
  - `PYTHON_VERSION=3.11.9` (або інша версія 3.11+).

Flask-сервер працює в окремому daemon-потоці й слухає `0.0.0.0:$PORT`.
Основний бот працює через `run_polling(drop_pending_updates=True)`.
Окремий daemon-потік раз на 30 секунд переводить прострочені утримання в
`expired`; додатково перевірка виконується при кожному зверненні до БД.

SQLite-файл `bot.db` створюється автоматично. На Render файлова система
контейнера тимчасова: для збереження заявок після redeploy потрібен
**persistent disk** або зовнішня БД. Наприклад, для платного Render можна
змонтувати disk у `/var/data` і встановити `DB_PATH=/var/data/bot.db`.
Запускати кілька екземплярів бота з однією SQLite-базою не слід.

На безкоштовному плані Render сервіс може «засинати» без трафіку. Для
постійної роботи потрібен платний інстанс або зовнішній пінг health-ендпоінта.

## Бізнес-логіка

- Послуги мають ціну, тривалість і опис; слоти генеруються з кроком 30 хвилин
  з урахуванням робочих годин, перерви та тривалості послуги.
- Запис відкритий на `BOOKING_DAYS_AHEAD` днів; минулі дати й час не показуються.
- При виборі часу створюється утримання на 5 хвилин. Зайнятий або утримуваний
  інтервал не показується іншим клієнтам.
- Перетини перевіряються за інтервалами в SQLite (`BEGIN IMMEDIATE` +
  перевірка активної тривалості), а не лише за однаковим часом старту.
- «Скасувати вибір», «Назад», вихід у меню або `/menu` звільняють утримання.
- Підтвердження перетворює утримання на заявку `pending`; таймер більше не діє.
- Майстер підтверджує (`confirmed`) або відхиляє (`rejected`); після відхилення
  слот звільняється.
- Клієнт може скасувати власний `pending`/`confirmed` запис не пізніше ніж за
  `CANCELLATION_CUTOFF_MINUTES` до початку. Пізніше — лише телефоном.
- Майстер отримує сповіщення про нову заявку; клієнт — про підтвердження або
  відхилення. Помилка доставки лише логується й не скасовує зміну в БД.
- Адмін-список має фільтри «Очікують / Підтверджені / Усі» та пагінацію.

## Міграція та дані

`init_db()` при старті створює таблицю й індекси, а для старої бази додає
нові колонки `price_label` і `duration_minutes`. Старі демо-ідентифікатори
часів `t1…t5` читаються як 10:00…18:00, тому вже створені записи не ламають
перевірку перетинів. Дані не видаляються автоматично; історія статусів
залишається в `bookings`.

## Що замінити перед реальним запуском

Демонстраційні дані зібрані в `config.py`:

- `ADDRESS`, `PHONE`, `PHONE_URI`, `INSTAGRAM_URL`, `WORKING_HOURS`;
- `SERVICES` — назви, ціни, тривалість, опис;
- `WORKING_HOURS_BY_WEEKDAY`, `BREAKS`, `SLOT_STEP_MINUTES`,
  `BOOKING_DAYS_AHEAD` — графік і правила слотів;
- `CANCELLATION_CUTOFF_MINUTES` — правило скасування.

Поточні адреса й телефон позначені як демо. Замініть їх на реальні дані
перукарні. Редагування графіка з адмінки поки немає: він задається в
`config.py`, а екран «Розклад» показує поточні налаштування.

## Що реалізовано

- Головне меню, послуги з цінами/тривалістю/описом, контакти.
- Динамічні дати й слоти на найближчі дні; перерви та робочі години.
- 5-хвилинне утримання, захист від перетинів і подвійного запису.
- Заявки `held → pending → confirmed/rejected`, історія в «Мої записи».
- Скасування клієнтом за правилом, звільнення слота.
- Сповіщення майстру та клієнту з логуванням помилок доставки.
- Адмін-панель: фільтри заявок, пагінація, картка клієнта, дії майстра.
- Перевірка доступу до адмін-панелі та захист чужих заявок.
- `/start`, `/menu`, `/help`, `/admin`, health-сервер.

## Обмеження

- Один майстер (`ADMIN_CHAT_ID`). Для кількох майстрів потрібні `master_id`,
  окремі графіки й фільтрація слотів.
- Графік задається в `config.py`; редагування з адмінки — наступний етап.
- Немає оплат, нагадувань і телефону клієнта; картка майстра містить
  username/ID клієнта.
- Feature «Запропонувати інший час» — явна заглушка, заявка залишається
  `pending`.
- Активне утримання після рестарту зберігається в БД і блокує слот до
  істечення, але підтвердити його зі старого повідомлення після втрати
  `context.user_data` не можна.
- На free Render SQLite не переживе redeploy без persistent disk.
- Доставка сповіщень не має повторних спроб; помилки лише логуються.
